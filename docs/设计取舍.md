# 设计取舍

这些都是踩出来的。写下来省得后来人再踩一遍，也方便想改这个项目的人知道哪些地方是刻意的。

## 1. 装运行库必须管理员权限

所以 exe 的清单里直接写了 `requireAdministrator`（见 `ui/src-tauri/build.rs`），Windows 在进程启动前就完成提权，不会出现"先开一个普通窗口、再重启自己"的闪一下。

开发构建**不加**这个清单，否则每次改代码重建都要点一次 UAC，没法调试。

## 2. 不做"装没装"的检测，全部照装

安装器本身是幂等的（已经装了会返回 1638），而检测一旦判错，用户拿到的就是一台依然缺库的机器——漏装的代价远大于多花几十秒。

唯一的例外是散装 dll（VB5/VB6、CRT 2002/2003）只补缺：正在被程序加载的系统 dll 覆盖会失败（共享冲突），而这一类"文件在就能用"。

## 3. MSI 不能从非 ASCII 路径安装

Windows Installer 服务是独立进程，包路径要在它内部过一遍 ANSI 转换，中文路径到那儿就成乱码，`msiexec` 只会回 **1619（安装包打不开）**。

所以程序会先把 MSI 连同它的 CAB 拷到 `C:\ProgramData\Click\<组件>\` 再装——这样跟我们自己装在哪儿、用户把程序放哪儿都无关。

## 4. 每一代安装器的静默开关都不一样

2005 只认 `/Q`；2008/2010 是 `/Q /NORESTART`；2012 之后才是 `/install /quiet /norestart`。参数在 `ui/src-tauri/src/lib.rs` 的组件表里逐条配。

## 5. "静默"不等于没有界面

老的自解压包用 `/Q` 只是它自己不出声，内部还会再调一次 `msiexec` 弹进度框。

所以 2005/2008/2010 是**把包拆开、直接调 `msiexec /qn`**，只有这样才是真的一点窗口都没有。拆出来的 MSI 少了同目录的 CAB 会失败（1620/1635），所以 MSI 和 CAB 必须一起带。

## 6. x86 和 x64 都要装

32 位程序读 `SysWOW64`、64 位读 `System32`，两套是分开的。老游戏和老工具绝大多数是 32 位，只装 64 位的话它们照样缺库。

## 7. 不含 VSTOR（VS 2010 Tools for Office）

那是给老 Office 的 VSTO 插件用的运行时，跟游戏无关；而且它在 64 位系统上装不上：x64 那份的 MSI 要同目录有 `install.ini`（缺了报 1308），x86 那份的 MSI 里写死了 `CA_BlockOnAMD64` 直接拒绝在 64 位安装。

## 8. 单文件

运行库整个以 zip 形式内嵌在 exe 里（`ui/src-tauri/payload.zip`，Rust 的 `include_bytes!` 是编译期解析路径，所以这个文件必须落在源码树里，已在 `.gitignore` 中），首次运行解到 `C:\ProgramData\Click\payload\<版本>\`，之后复用。

所以发出去就是一个文件，不需要安装程序，也没有卸载器。

## 9. 安装期间锁住关闭

半截被打断最难收拾。界面上把关闭键压暗禁用，后端也拦一道（`ui/src-tauri/src/lib.rs` 里的 `BUSY`），Alt+F4 和任务栏"关闭窗口"同样进不来。

## 10. 改完图标要记得

换了 `ui/src-tauri/icons/` 之后直接构建，exe 里嵌的图标**不会更新**：tauri-build 的 build script 只监视 `tauri.conf.json`，资源脚本不会重跑。

```powershell
(Get-Item ui\src-tauri\tauri.conf.json).LastWriteTime = Get-Date   # touch 配置
cargo clean -p click                                              # 或者清产物（在 ui\src-tauri 下）
```

判断有没有生效：从 exe 里把图标抠出来看一眼，别看资源管理器——它有图标缓存，同一个路径会给你看旧的。

## 11. 1612：Windows 记着的安装源不在了

用户机器上真撞到的：那台机器的 2008 / 2010 以前是从别家的合集装的，那个合集把 MSI 解到 `D:\随机名\` 里装完就删；而 Windows 自己的包缓存（`C:\Windows\Installer\*.msi`）又被清理工具扫掉了。此后再装同一套运行库，`msiexec` 是在"修"旧记录——它按记录里的源目录找包，压根不看我们命令行上给的这份，于是稳定回 **1612（安装源不存在）**，重跑多少次都一样。

查这台机器上装成功过的产品，`SourceList` 长这样（本地目录是登记在 `Net` 里的，不是 `Media`）：

```
LastUsedSource = n;4;C:\ProgramData\Click\vc2008_x86\
Net  1=e:\67434078…\   2=e:\8277aefa…\   3=C:\WINDOWS\Temp\Click\…\   4=C:\ProgramData\Click\vc2008_x86\
```

所以补救按"命中率"从高到低排：

1. **把包放回记录里那个目录**。`MsiSourceListGetInfo` 读出 `LastUsedSource`（真机上返回的是纯路径，不是注册表里那种 `n;4;…`），把 `vc_red.msi` 和 CAB 原样放回去，然后重试 `/i`——`msiexec` 要的就是这个，不需要跟它讲道理。只在本地绝对路径、那个盘还在的时候做（UNC、http、拔掉的 U 盘都跳过）。
2. 还不够就用官方 API 补源：`MsiSourceListAddSourceEx` 追加（机器上下文，实测用户上下文对这些产品直接回 1605），再把 `LastUsedSource` 改写成我们的目录，最后用 `msiexec /f <包> REINSTALL=ALL REINSTALLMODE=vomus` 强制从手上这份重装。

每一次调用的返回码都原样写进日志——这件事没有可复现的机器就只能靠现场日志判断。

顺带一个认知：第一版只做了第 2 条的"追加源"，在一台真机上没用（`install-retry.log` 里它还是去找那个死掉的 `d:\…`）。**Windows 先认 `LastUsedSource`，而追加源不会改它。**

推出来的规矩：各组件目录里的 MSI / CAB **不能**像 payload 那样删。那是登记过的安装源，删了以后这台机器上这几代的修复、重装、打补丁都会回到 1612。payload 可以删，因为它只是复制过去的东西的源头，删了解一次就有。
